# SPB-NAS1: разделение файловой и VM-storage сети

**Дата:** 2026-09-29  
**NAS:** `SPB-NAS1` / `spb-file-cloud`

## Назначение

Развести пользовательскую файловую шару и будущий datastore VM на разные
физические 10GbE интерфейсы NAS. Это необходимо, поскольку DSM не позволяет
штатно одновременно держать два L3-сервиса на существующем bond.

## Итоговая сетевая схема

| Роль | NAS интерфейс | IP | H3C / порт | VLAN | Шлюз |
|---|---|---|---|---|---|
| Management DSM | `eth1` | `10.78.0.250/24` | без изменений | management | нет default route |
| SMB / Drive / текущий NFS | `eth7` | `10.78.7.10/24` | H3C-1 upper `XGE1/0/54:2` | access 1070 | `10.78.7.254` |
| VM storage | `eth4` | `10.78.5.10/24` | H3C-2 lower `XGE1/0/54:2` | access 1050 | нет |

`bond0` удалён. `eth4` и `eth7` больше не являются резервом друг для друга:
это осознанная временная цена за независимое L2-разделение без третьего 10GbE
интерфейса.

## Выполненные изменения

1. Снята реальная привязка кабелей по MAC: активный прежний `bond0 eth4`
   подключён к нижнему H3C, а `eth7` — к верхнему.
2. Удалён DSM Link Aggregation `bond0` (active/standby, slaves `eth4 eth7`).
3. DSM назначил прежний `10.78.7.10` на `eth4`; он был перенесён на `eth7`.
4. На `eth4` назначен `10.78.5.10/24`.
5. Нижний H3C `XGE1/0/54:2` переведён из access VLAN1070 в access VLAN1050;
   верхний `XGE1/0/54:2` оставлен access VLAN1070.
6. После приёмки storage default route перенесён на файловый сервис:
   `10.78.7.254 dev eth7`. Management `eth1` сохранил прямую connected route
   к `10.78.0.0/24`.

## Приёмка

- PVE1/PVE2 → `10.78.7.10` по `vmbr0.1070`: 5/5;
- PVE1/PVE2 → `10.78.5.10` по `ens2f1`: 5/5;
- PVE3 → `10.78.7.10`: 5/5;
- NAS → PVE1 по обоим новым сервисным адресам: 3/3;
- интернет с NAS через `eth7`: ICMP до `1.1.1.1` 3/3 и HTTPS `200` до
  `example.com`;
- на PVE1/PVE2 по 4 iSCSI sessions, все 8 MSA paths
  `active/running/ready`; кластер quorate 3/3;
- текущий `synology-exchange-dag` NFS datastore через `10.78.7.10` остаётся
  active.

## Важное ограничение и следующий этап

NFS datastore **ещё не перенесён** с `10.78.7.10` на `10.78.5.10`:

- DSM NFS ACL сейчас ограничен прежними клиентами `10.78.7.201-203`;
- `spb-pve3` не имеет физического пути Fabric B / `10.78.5.0/24`.

Перед переносом пустого datastore надо отдельно: добавить ограниченные ACL для
`10.78.5.11` и `.12`, изменить PVE storage endpoint и принять решение по PVE3
(подключить к Fabric B или исключить из nodes данного storage). Не использовать
storage IP для пользователей и не маршрутизировать VLAN1050.

## Откат

При необходимости вернуть прежнюю сетевую отказоустойчивость файлового
сервиса:

1. вернуть H3C-2 `XGE1/0/54:2` в access VLAN1070;
2. удалить `10.78.5.10` с `eth4`;
3. создать DSM active/standby bond из `eth4 eth7` и назначить ему
   `10.78.7.10/24`;
4. проверить PVE1–PVE3 до файлового IP.

Этот откат удалит отдельный VM-storage путь. Management `eth1` в нём не
участвует.

## Восстановление после Mode 1 reset — 2026-09-30

Mode 1 reset сбросил все интерфейсы в DHCP. Фактическое исходное состояние
перед восстановлением:

```text
eth1  10.78.0.250/24, default via 10.78.0.254   (DHCP reservation, management)
eth4  169.254.68.128/16                         (link UP, lower storage fabric)
eth7  169.254.183.114/16                        (link UP, upper file fabric)
```

План восстановления, не затрагивающий management `eth1`:

1. `synonet --manual eth4 10.78.5.10 255.255.255.0`;
2. проверить связь NAS ↔ PVE1/PVE2 по `10.78.5.0/24`;
3. `synonet --manual eth7 10.78.7.10 255.255.255.0`;
4. проверить связь NAS ↔ PVE1/PVE2/PVE3 по `10.78.7.0/24`;
5. только при успешных проверках: `synonet --set_gateway 10.78.7.254`;
6. проверить исходящий HTTPS NAS и сохранить SSH через management.

Откат к состоянию сразу после reset:

```bash
synonet --dhcp eth4
synonet --dhcp eth7
synonet --set_gateway 10.78.0.254
```

### Фактически выполнено и проверено

Выполнено через DSM `synonet` без изменения H3C, PVE, NFS-экспорта, пулов или
файловых ACL:

```bash
synonet --manual eth4 10.78.5.10 255.255.255.0
synonet --manual eth7 10.78.7.10 255.255.255.0
synonet --set_gateway 10.78.7.254
```

На момент приёмки оба 10GbE-интерфейса были `UP`; NAS успешно пинговал
`10.78.5.11`, `10.78.5.12` через `eth4`, а также `10.78.7.201`–`10.78.7.203`
и `10.78.7.254` через `eth7` (по 3/3). DNS через `10.78.0.254` отвечает.

Исходящий Интернет с файлового адреса пока намеренно не восстановлен: на
AL-OBIT действует явное правило `synology drop` (`chain=forward`,
`src-address=10.78.7.10`, `out-interface-list=WAN`, `action=drop`). Это не
сетевая ошибка NAS и не было изменено в рамках восстановления после reset.
Для безопасного возврата обновлений NAS требуется отдельное согласованное
исключение перед этим правилом только для исходящих `TCP/80,443`; входящие
подключения не нужны.

После приёмки повторный SSH-контроль не прошёл: NAS отверг пароль и ключ
пользователя `ansible`. Это тот же независимый инцидент с правами/учётной
записью и не является следствием назначения IP-адресов. Повторно выполнять
`synogroup --member administrators` нельзя: ранее этот запрос коррелировал с
потерей локальных прав администратора.

Reboot/relogin не требуется для сетевой конфигурации. Следующая проверка после
восстановления доступа: повторить пинги выше и проверить активность NFS
datastore с PVE1/PVE2.

После успешного восстановления management остаётся DHCP-reservation
`10.78.0.250`; DNS `10.78.0.254` сохраняется.
