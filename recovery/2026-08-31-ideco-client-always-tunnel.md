# Ideco Client: принудительный туннель для всех сетей

## Задача

Убрать различие между локальным и внешним подключением: любой успешный вход
Ideco Client должен создавать туннель.

## Изменение

На `IDECO-SPB-PILOT` (`192.168.203.82`) в persistent etcd
`http://127.0.0.1:2379`, ключ
`/agent-server-ng/settings/v6/record`, изменено только:

```json
"local_tunnel": "without_tunnel" -> "with_tunnel"
```

Сохранены публичный FQDN `ngfw.aurora-logistics.ru` и ограничение
пользовательской авторизации группой `Net-Ideco-Pilot`.

## Проверка

- значение ключа после записи: `local_tunnel = with_tunnel`;
- `ideco-agent-backend`, `ideco-agent-websocket` и
  `ideco-websocket-vpn-server@agent` — `active`;
- Agent снова слушает TCP `14765`;
- WebSocket/VPN-служба штатно пересобрала `LagentWG_srv`.

## Откат

Точное предыдущее JSON-значение сохранено на NGFW:
`/var/lib/ideco-support/20260831-agent-always-tunnel/agent-settings.before.json`.
Восстановить его в тот же etcd-ключ через `etcdctl` с
`ETCDCTL_ENDPOINTS=http://127.0.0.1:2379`; Agent автоматически применит
изменение. Перезагрузка NGFW не нужна. Клиентам потребуется переподключиться.

## Дальше

На тестовом клиенте отключить и подключить профиль заново, затем проверить
наличие нового Agent VPN-сеанса и доступ к Интернету.

## Full-tunnel Internet (12:49 MSK)

После включения туннеля для локальной сети клиент успешно получал адрес
`10.128.0.3`, но продолжал видеть портал: стандартное правило передачи
маршрутов имело `mode: utm` и не передавало `0.0.0.0/0` в Agent VPN.

В `http://127.0.0.1:2379`, ключе
`/vpn-servers/route_rules/v2/records/1`, изменён только режим передачи
маршрутов на `mode: all` (объекты остаются `any`, правило включено). Это
соответствует опции Ideco «Отправлять весь трафик на NGFW».

Точное прежнее значение:
`/var/lib/ideco-support/20260831-agent-vpn-full-tunnel/route-rule.before.json`.
Для отката записать этот JSON в тот же etcd-ключ; затем клиент должен
переподключиться. Перезагрузка NGFW не нужна.

## Automatic SNAT for Agent VPN egress (13:01 MSK)

Full-tunnel пакеты из `10.128.0.0/16` уходили через `Eeth4` с исходным
адресом клиента и не получали ответов. Пользовательское SNAT-правило с
транзитным IP не применилось: Novum поддерживает такой SNAT только на адрес
Loopback. Оно удалено без остатка.

По явному подтверждению включён штатный параметр
`/firewall/settings/v5/record.automatic_snat_enabled = true`. Его правила
маскируют private источники (`10/8`, `172.16/12`, `192.168/16`) при выходе
через WAN-интерфейсы, включая Agent VPN-пул на `Eeth4`.

До включения удалены только conntrack-состояния `10.128.0.2` (87 записей),
чтобы новые соединения сразу выбрали NAT. WireGuard-сеанс не сбрасывался.
Новые TCP-сессии уже показывают обратные пакеты через `172.31.146.2`.

Откат: восстановить
`/var/lib/ideco-support/20260831-enable-automatic-snat/firewall-settings.before.json`
в тот же ключ на `127.0.0.1:2379`; при необходимости очистить только
conntrack Agent VPN-клиентов. Перезагрузка не нужна.
