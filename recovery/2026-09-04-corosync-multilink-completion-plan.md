# Завершение выделенных сетей Corosync для SPB-OBIT-DC

Дата составления: 2026-09-04. Статус: выполнено и проверено 2026-09-04.

## Цель

Завершить три независимых пути Corosync для кластера `SPB-OBIT-DC`:

| Узел | link0 (текущий) | link1, VLAN 1060 | link2, VLAN 1061 |
|---|---|---|---|
| spb-pve1 | 10.78.2.201 | 10.78.6.1/29 | 10.78.6.9/29 |
| spb-pve2 | 10.78.2.202 | 10.78.6.2/29 | 10.78.6.10/29 |
| spb-pve3 | 10.78.2.203 | 10.78.6.3/29 | 10.78.6.11/29 |

`link1` проходит через H3C upper (`10.78.2.11`), `link2` — через H3C lower
(`10.78.2.12`). На PVE1/PVE2 VLAN работают поверх существующих iSCSI NIC с
native VLAN 1; на PVE3 используются отдельные `eno3`/`eno4`.

## Подтверждённое состояние на 2026-09-04

- кластер quorate 3/3, Corosync config version 12, активен только link0;
- PVE1: `ens2f0.1060 = 10.78.6.1/29` и
  `ens2f1.1061 = 10.78.6.9/29` созданы, применены и подняты;
- PVE3: `eno3.1060 = 10.78.6.3/29` и `eno4.1061 = 10.78.6.11/29`
  созданы, применены и подняты;
- PVE1 и PVE3 доступны друг другу по обоим VLAN в обоих направлениях;
  MTU 1500 с DF проходит, потерь и ошибок нет;
- upper: VLAN 1060 tagged на `XGE1/0/5` (PVE3), `XGE1/0/49:1` (PVE1) и
  `XGE1/0/49:2` (PVE2);
- lower: VLAN 1061 tagged на `XGE1/0/5` (PVE3) и `XGE1/0/49:1` (PVE1);
- lower `XGE1/0/49:2` (PVE2) ещё не пропускает VLAN 1061;
- на PVE2 отсутствуют `ens2f0.1060` и `ens2f1.1061`.

## Общие ограничения

- Выполнять этапы последовательно; не менять Corosync до полного прохождения
  L2/L3-проверок всеми тремя узлами.
- Перед каждым изменением делать readback и резервную копию затрагиваемого
  конфига. После каждого изменения проверять management, iSCSI и quorum.
- На PVE применять сеть штатным Proxmox API/reload, не перезапускать узел.
- Не менять native VLAN 1, адреса `10.78.4.0/24` и `10.78.5.0/24`, bond,
  bridge, gateway, MSA, STP, BAGG и несвязанные порты.
- На H3C сохранять startup-конфигурацию только после успешного readback.
- Пароли не записывать в файлы; получать их из KeePass через Secret Service.
- При потере SSH, quorum, iSCSI-связности либо неожиданном diff немедленно
  остановиться и выполнить откат текущего этапа.

## Этап 1. Снимок перед изменениями

1. Проверить `pvecm status`, `corosync-cfgtool -s`, failed units и журналы
   Corosync на всех PVE.
2. Сохранить на PVE2 копию `/etc/network/interfaces` с timestamp и mode 0600.
3. Сохранить копию `/etc/pve/corosync.conf` вне pmxcfs как mode 0600.
4. На обоих H3C снять current/startup readback VLAN 1060/1061 и портов
   `XGE1/0/49:1`, `XGE1/0/49:2`, `XGE1/0/5`.
5. Проверить доступность используемых iSCSI endpoints с PVE1/PVE2 и состояние
   storage в Proxmox. Зафиксировать baseline счётчиков интерфейсов.

Условие перехода: quorum 3/3, link0 connected, storage доступно, неожиданных
failed units и сетевых ошибок нет.

## Этап 2. Закончить VLAN 1061 на порту PVE2

На H3C lower изменить только `Ten-GigabitEthernet1/0/49:2`:

- сохранить native VLAN 1 untagged;
- перевести/оставить порт в hybrid;
- добавить VLAN 1061 tagged;
- установить описание `lower srv sfp port B + corosync-ring2`;
- сохранить остальные параметры, включая `undo jumboframe enable` и
  `flow-control`.

После изменения проверить текущую конфигурацию порта, VLAN 1061, состояние
линка, отсутствие ошибок и сохранение iSCSI PVE2. Затем выполнить `save force`
и повторный readback startup-конфигурации.

Откат этапа: удалить только tagged VLAN 1061 и вернуть исходное описание на
`XGE1/0/49:2`, не трогая native VLAN 1 и остальные параметры; сохранить.

## Этап 3. Создать VLAN-интерфейсы PVE2

Через Proxmox API создать:

- `ens2f0.1060`, raw device `ens2f0`, VLAN ID 1060,
  `10.78.6.2/29`, autostart;
- `ens2f1.1061`, raw device `ens2f1`, VLAN ID 1061,
  `10.78.6.10/29`, autostart.

Не задавать gateway, bridge или bond. До применения проверить pending diff:
он должен содержать только эти два интерфейса. Применить штатным network reload.

Проверка: SSH доступен; default route остался через `vmbr0` и `10.78.2.254`;
native iSCSI-адреса не изменились; оба VLAN-интерфейса `UP/LOWER_UP`; quorum
3/3; storage доступно; failed units отсутствуют.

Откат этапа: удалить только два новых VLAN-интерфейса через Proxmox API и
применить reload. При потере управления восстановить backup с локальной/BMC
консоли.

## Этап 4. Полная L2/L3-приёмка

С каждого PVE проверить оба адреса остальных узлов с явно заданным исходным
VLAN-интерфейсом:

- обычный ping серией не менее 20 пакетов;
- ping с DF и payload 1472 для подтверждения MTU 1500;
- MAC/neighbor mapping и правильный исходный адрес;
- counters до и после теста.

На H3C подтвердить, что в VLAN 1060 и 1061 изучены ровно ожидаемые MAC PVE1,
PVE2 и PVE3 на ожидаемых портах. Проверить CRC, drops, carrier errors и link
flapping. Отдельно повторить проверку iSCSI/storage и quorum.

Условие перехода: полная матрица 3×3 работает в обоих VLAN, 0% потерь, MTU
1500 проходит, нет ошибок, management и storage не деградировали.

## Этап 5. Включить Corosync multilink

Проводить в согласованное окно. Перед записью ещё раз сохранить актуальный
`corosync.conf` и проверить quorum 3/3.

В едином изменении `/etc/pve/corosync.conf`:

1. Увеличить `config_version` с 12 до 13 (либо на единицу от фактического).
2. Добавить каждому node соответствующие `ring1_addr` и `ring2_addr` из
   таблицы цели.
3. В секцию `totem` добавить интерфейсы с `linknumber: 1` и `linknumber: 2`,
   сохранив существующий `linknumber: 0`.
4. Сохранить `link_mode: passive` и прочие действующие тайминги без изменений.

Не редактировать локальные копии на разных узлах: `/etc/pve/corosync.conf`
является кластерным файлом pmxcfs. После записи не выполнять ручной массовый
restart Corosync; наблюдать штатное применение конфигурации.

Немедленная проверка на всех узлах:

- `pvecm status`: 3/3 и Quorate;
- `corosync-cfgtool -s`: links 0, 1, 2 известны, peers connected;
- runtime cmap содержит все три адреса каждого узла;
- журналы Corosync не содержат постоянного flapping, PMTU или auth errors;
- management, storage и failed units без изменений.

Откат: восстановить структуру исходного файла без ring1/ring2, но установить
новый, ещё больший `config_version`; проверить link0 и quorum. Не копировать
старый version 12 поверх уже применённой версии 13.

## Этап 6. Испытания отказоустойчивости

Проводить по одному воздействию с полным восстановлением между тестами:

1. На одном узле временно разорвать link0 и подтвердить сохранение membership
   через link1/link2.
2. Восстановить link0 и дождаться состояния connected всех links.
3. Аналогично проверить отдельный отказ link1, затем link2.
4. Отказ целого H3C проверять только отдельным согласованным тестом после
   успешных интерфейсных тестов.

Во время каждого теста непрерывно следить за `pvecm status`, knet links,
журналом Corosync и storage. Никогда не отключать одновременно несколько
путей и не тестировать несколько PVE параллельно.

Критерий приёмки: узел не покидает membership, quorum не теряется, ВМ и
storage не получают нарушений, восстановленный link возвращается в connected.
