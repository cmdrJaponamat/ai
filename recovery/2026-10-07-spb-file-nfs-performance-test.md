# Проверка производительности старой полки SPB-FILE

**Дата:** 2026-10-07  
**Полка:** `spb-file`, `10.78.2.210`  
**Клиент:** PVE2, `10.78.2.202`  
**Экспорт:** NFSv4 `10.78.2.210:/volume1/main`, storage `synology`

## Методика

После восстановления NFS-службы на полке с PVE2 выполнен однопоточный
последовательный тест direct I/O: запись и чтение временного файла 4 GiB,
блок 64 MiB. `oflag=direct`/`iflag=direct` исключили влияние page cache
клиента. Файл и временный каталог успешно удалены после теста.

## Результат

| Операция | Результат |
| --- | --- |
| Запись | **113,3 MB/s** |
| Чтение | **88,6 MB/s** |

Это результат одного последовательного потока NFS с PVE2; он не является
гарантией для многопользовательского SMB, мелких файлов или случайного I/O.
Скорость записи практически упирается в уровень 1 Gb/s (теоретический предел
около 125 MB/s).

## Вывод

Полка годится для вторичного последовательного хранилища резервных копий при
достаточной ёмкости: текущий NFS-экспорт имел около 3,7 TiB свободного места.
Однако её не следует сейчас выбирать для переноса основной пользовательской
SMB-шары:

- скорость не даёт запаса над гигабитным уровнем;
- до теста NFS-служба зависла на простой операции удаления и потребовала
  перезапуска;
- для SMB существенны конкурентная работа и latency, которые этот тест не
  улучшает и не измеряет.

Под «офлайн-бэкапом» не следует понимать постоянно смонтированный NFS/SMB
ресурс: такой ресурс остаётся доступным при компрометации ЦОДа. Для защиты от
шифровальщика нужны отдельные учётные данные/ACL, snapshots с retention и,
если требуется действительно offline-копия, отключение/ротация носителя или
экспорта вне окна бэкапа.

## Откат

Конфигурация полки, PVE и NFS не менялась. Временный файл удалён; перезагрузка
PVE не требовалась.
