# PortalAL: ответ исполнителя не отправлялся из браузера без crypto.randomUUID

Дата: 18.11.2026. Пользователь сообщил ошибку `crypto.randomUUID is not a function` при ответе в заявке.

Причина: `src/api/serviceDeskOperatorApi.ts` напрямую вызывал `crypto.randomUUID()` для ключа идемпотентности. На внутреннем HTTP-адресе браузер может не предоставлять этот API. Создание заявки и ответ заявителя уже использовали `newServiceDeskIdempotencyKey()` с совместимым вариантом.

Изменение: PR #12, коммит `2c3ff6d`, merge `fc8a8974f1f26c22912462a15fe642290f02968d`. Ответ исполнителя, внутренняя заметка и изменение атрибутов теперь получают ключ через существующий генератор. Другие подсистемы и доступ к прямому HESK не менялись.

Проверка: тест моделирует отсутствие `crypto.randomUUID`, отправку ответа и повтор после сетевой ошибки с тем же ключом; локально `npm test` 80/80 и `npm run build` прошли. CI PR #12 прошёл. Пользователь разрешил не ждать обычной цепочки CI/staging; вручную запущен workflow `Deploy production` run 44273021839 для `main`. Workflow успешно собрал образ `portal-al:fc8a8974f1f26c22912462a15fe642290f02968d`, скрипт deployment дважды подтвердил health-check и завершился без отката. Авторизованная отправка ответа реальным пользователем после выпуска ещё не проверена.

Откат: штатно развернуть предыдущий образ `portal-al:0fc68dda65ad0da6e8e3d08dbfde09521a24824a` по процедуре `deploy/deploy-image.sh` либо revert PR #12 и дождаться CI/CD. Перезапуск ОС не нужен; контейнер пересоздан deployment workflow. Пользователю достаточно обновить страницу, при кэшировании — принудительно обновить.
