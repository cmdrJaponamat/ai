# Безопасный запуск сервера Veeam

**Дата:** 2026-10-07  
**Гипервизор:** PVE2, `10.78.2.202`  
**Сервер Veeam:** VM 131 `spb-veeam`  
**Worker:** VM 133 `worker-veeam`

## Цель

Вернуть в работу давно выключенный сервер Veeam, не допустив автоматического
старта устаревших заданий резервного копирования.

## Выполненные действия

1. Проверено, что задания Proxmox Backup Server не включают VM 131 и VM 133.
2. Сохранена конфигурация VM 131 на PVE2:
   `/root/131.conf.pre-veeam-isolated-start-20261007`.
3. У VM 131 отключён автозапуск (`onboot: 0`), чтобы её последующая
   перезагрузка гипервизора не запускала Veeam без явного решения.
4. VM 131 запущена сначала с отключённым линком `net0` (`link_down=1`). Это
   позволило открыть Veeam Backup Service и проверить задания без сетевого
   доступа к источникам, репозиториям и защищаемым системам.
5. В Veeam отключено расписание всех обнаруженных заданий:

   | Задание | Тип | Расписание после проверки | Запущено |
   | --- | --- | --- | --- |
   | `bkp_share_old` | NAS backup | Нет | Нет |
   | `bkp_1C_db` | Agent backup | Нет | Нет |
   | `bkp_exchange_volumes` | Agent backup | Нет | Нет |
   | `bkp_exchange_entire_vm` | Agent backup | Нет | Нет |
   | `bkp_share` | NAS backup | Нет | Нет |

6. После повторного чтения состояния линк VM 131 включён обратно. Гостевой
   адаптер `Ethernet` имеет состояние `Up`, 1 Gb/s, MAC
   `BC-24-11-EA-04-98`. Никакое задание после возврата сети не запустилось.
7. На момент первоначальной проверки VM 133 не запускалась. Позднее по
   отдельному указанию владельца VM 133 `worker-veeam` была запущена без
   изменения её дисков, сети или автозапуска. На PVE2 она имеет состояние
   `running`; QEMU Guest Agent в этой Linux VM не установлен/не запущен, поэтому
   IP и службы через `qm guest exec` не опрашиваются.

## Текущее безопасное состояние

- `spb-veeam` работает и доступен по сети, но не запустится сам после
  перезагрузки PVE2;
- все известные задания Veeam отключены по расписанию;
- `worker-veeam` запущен, но по-прежнему не имеет `onboot`;
- перед включением конкретного задания необходимо отдельно проверить его
  источники, репозиторий, retention и окно запуска.

## Откат

Для немедленной изоляции сервера на PVE2:

```bash
sudo qm set 131 --net0 e1000=BC:24:11:EA:04:98,bridge=vmbr0,link_down=1
```

Для остановки VM:

```bash
sudo qm shutdown 131
```

Для остановки worker при отсутствии необходимости:

```bash
sudo qm shutdown 133
```

Исходная конфигурация VM сохранена по указанному выше пути. Восстанавливать
её следует только если потребуется вернуть прежний `onboot` или параметры
сетевого адаптера.

## Инцидент при попытке подготовки HA (2026-10-07)

При подготовке VM131 к PVE HA был начат перенос её единственного 100 GiB
диска с локального `local-zfs` PVE2 в shared `lvm_pathb`. Внешнее ожидание
операции завершилось до завершения `qm move_disk`; затем ошибочно был удалён
целевой LVM-том, принятый за незавершённый, в момент, когда Proxmox уже
переключил конфигурацию VM и автоматически удалил исходный ZFS-том.

Проверка LVM-архива позволила восстановить метадату удалённого target-LV по
точным физическим extent'ам, однако консоль VM показала `Boot failed: not a
bootable disk` и переход в PXE. Это подтверждает, что в target была только
неполная копия (во время наблюдения перенос дошёл примерно до 22%).

Текущее состояние после инцидента:

- VM131 выключена, `onboot=0`;
- её восстановленный, но незагрузочный LV
  `lvm_pathb:vm-131-disk-0` намеренно оставлен нетронутым;
- исходный `local-zfs:vm-131-disk-0` и штатные PBS/NFS backup VM131 не
  найдены; снимков ZFS также не найдено;
- VM131 **не** добавлена в HA;
- VM133 и VM135 не изменялись этой операцией.

Не выполнять на PVE2 операции записи/выделения на `lvm_pathb` без отдельного
плана восстановления, если требуется пытаться извлечь данные из неполного
target-LV. Практический путь возобновления Veeam после решения владельца —
развернуть новую VM131/Veeam и подключить существующий Linux repository;
это не восстановит конфигурационную БД Veeam без отдельной её резервной копии.
