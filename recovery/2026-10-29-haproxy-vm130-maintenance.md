# HAProxy VM130: обновление и подготовка пилота

Дата: 2026-10-29.
Статус: завершено 2026-10-29.

## Цель

Без изменения KSMG, MikroTik NAT, Exchange или рабочих frontend-конфигураций
обновить существующую VM130 `haproxy` (`10.78.3.133`, PVE2) и подготовить её
к последующему пилоту L4-балансировки Exchange.

## Исходное состояние

- VM130 работает на PVE2, Debian 12, 2 vCPU, 2 GiB RAM, 16 GiB local-zfs;
- HAProxy 2.6.12 активен и слушает TCP/443;
- текущий `haproxy.cfg` обслуживает отдельный существующий HTTPS web backend,
  поэтому очищать либо перепрофилировать VM в этом окне запрещено;
- `apt list --upgradable` показывает обновления ОС, OpenSSL/OpenSSH,
  QEMU Guest Agent и kernel;
- PVE2 имеет 1.33 TiB свободно на `rpool`; существующих PVE-снимков VM130 нет.

## Выполнено

- На PVE2 перед изменениями создан снимок VM130
  `pre-upgrade-20261029` с описанием отката.
- Выполнены `apt update`, `apt full-upgrade`, затем завершена прерванная
  конфигурация пакетов через `dpkg --configure --pending`.
- Обновлены, в частности, HAProxy, OpenSSL/OpenSSH, QEMU Guest Agent и Debian
  kernel; VM штатно перезагружена.
- После загрузки: kernel `6.1.0-54-amd64`; `dpkg --audit` не выводит проблемных
  пакетов; конфигурация `/etc/haproxy/haproxy.cfg` валидна; службы `haproxy` и
  `qemu-guest-agent` имеют состояние `active`; TCP/443 слушает на `0.0.0.0`.
- Существующая конфигурация HAProxy, KSMG, Exchange и MikroTik NAT не менялись.
  Поэтому текущий web backend на VM130 сохранён.

## Перенос HAProxy-1 в DMZ

- Перед сетевым изменением создан снимок PVE2 VM130
  `pre-vlan1100-20261029`; на AL-OBIT сохранён экспорт
  `pre-haproxy-vlan1100-20261029.rsc`.
- На AL-OBIT создан L3 SVI `VLAN1100-DC-DMZ-PUBLISHED` на `bridge`, VLAN ID
  1100, адрес `10.78.10.1/27`. L2 VLAN1100 уже был передан tagged через
  `bridge` и `LAG-SW` до PVE.
- VM130 временно получила второй NIC VLAN1100, на нём проверены шлюз и TCP к
  обоим HAProxy backend с исходным адресом `10.78.10.4`.
- После проверки старый NIC/адрес `10.78.3.133` удалён, VM130 оставлена с
  единственным NIC VLAN1100 (`BC:24:11:38:38:A0`) и статическим адресом
  `10.78.10.4/27`, шлюзом `10.78.10.1`.
- VM130 перезагружена для проверки сохранности: сеть, `haproxy` и QEMU Guest
  Agent восстановились; HTTPS через новый адрес вернул HTTP 200.
- DNS и публичные NAT не менялись: внешний TCP/443 по-прежнему направлен на
  nginx `10.78.3.1`. Непосредственно к HAProxy сейчас подключаются только
  явно использующие `10.78.10.4` внутренние клиенты.

## Наблюдение

В `/etc/hosts` гостя имя шаблона `template-debian` заменено на собственное
`haproxy`; предупреждение `sudo` о локальном разрешении имени устранено.

## Следующий этап: адресация HA-пары

Для HAProxy-пары зарезервированы адреса `10.78.10.4/27` (HAProxy-1),
`10.78.10.5/27` (HAProxy-2) и `10.78.10.6/27` (плавающий `mail-vip`) в
VLAN1100/DMZ; шлюз после включения сегмента — `10.78.10.1`. Nginx и KSMG
остаются на их существующих адресах `10.78.3.0/24`; адреса VLAN1100 им в этом
этапе не резервируются. Адреса серверов Exchange VLAN1030 для этого не
использовать.

VM130 уже переведена в VLAN1100. Перед развёртыванием HAProxy-2 нужно отдельно
настроить keepalived, DNS/NAT и выполнить проверку конфликтов для его IP и VIP.

## Активная L4-конфигурация почтовых frontend

Конфигурация `/etc/haproxy/haproxy.cfg` на VM130 развёрнута из версии,
сохранённой в этом репозитории как `2026-10-29-haproxy-vm130.cfg`.

- `10.78.10.4:443` читает только TLS ClientHello: SNI
  `mail.aurora-logistics.ru` идёт напрямую на MX3/MX4; любой иной или
  отсутствующий SNI — на nginx `10.78.3.1:443`.
- `10.78.10.4:25`, `:587`, `:993` подготовлены к будущему cutover KSMG/NAT и
  балансируются между MX3/MX4. Сейчас DNS, KSMG и NAT на эти frontend не
  указывают.
- TLS не завершается на HAProxy; `send-proxy` не используется ни к Exchange,
  ни к nginx. У HAProxy настроен runtime socket
  `/run/haproxy/admin.sock` для read-only операционного контроля.
- HTTPS health check каждого MX выполняет TLS с mail-SNI и требует HTTP 200 от
  `/mapi/healthcheck.htm`; SMTP/Submission используют SMTP check, IMAPS — TLS
  check. По состоянию после reload: оба MX `UP/L7OK` на HTTPS и SMTP,
  `UP/L6OK` на IMAPS; nginx `UP/L6OK`.

Если health check обоих MX в одном backend станет отрицательным, новые
соединения к соответствующему frontend не будут направлены на Exchange и
закроются HAProxy. Уже установленные TCP-сессии живут до разрыва их текущего
соединения. KSMG классифицирует невозможность подключения как временную
ошибку и повторяет доставку из собственной очереди; keepalived при этом не
переносит VIP, поскольку HAProxy-узел остаётся здоровым.

## План изменения

1. Создать PVE snapshot VM130 перед обновлением.
2. Выполнить штатные `apt update` и full-upgrade внутри гостя.
3. Штатно перезагрузить VM, если обновление требует новый kernel.
4. Подтвердить QEMU Guest Agent, сеть, HAProxy и TCP/443, а также сохранение
   текущей конфигурации HAProxy.

## Откат

Для отката сетевого переноса остановить VM130 и откатить на PVE2 снимок
`pre-vlan1100-20261029`, затем удалить на AL-OBIT только адрес
`10.78.10.1/27` и интерфейс `VLAN1100-DC-DMZ-PUBLISHED`. Это возвращает
VM130 к `10.78.3.133` без изменения KSMG, Exchange и NAT. Для отката пакетов
использовать более ранний снимок `pre-upgrade-20261029`.

Для отката только mail frontend восстановить
`/etc/haproxy/haproxy.cfg.pre-mail-frontends-20261029` (либо более позднюю
копию `.pre-healthcheck-20261029`) как `/etc/haproxy/haproxy.cfg` и выполнить
`systemctl reload haproxy`. Перед включением frontend создан отдельный снимок
PVE `pre-mail-frontends-20261029`.

## Ожидаемое влияние

Перезагрузка VM кратко прервёт существующий HTTPS-трафик, проходящий через
VM130. Reboot PVE2 и перезагрузка Exchange не требуются.
