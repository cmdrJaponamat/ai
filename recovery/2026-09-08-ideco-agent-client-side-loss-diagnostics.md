# Ideco Agent: локализация потерь на Windows/DLP — 2026-09-08

## Симптом

На втором Windows-ПК с установленным DLP-клиентом «Стахановец» Ideco Client
подключался, но `ping 8.8.8.8` на ПК показывал тайм-аут. Его физический адрес
`10.76.40.83`, VPN-адрес `10.128.0.4`.

Первый наблюдавшийся peer `10.128.0.3` с endpoint `10.76.40.179` принадлежал
другому компьютеру: во время первого захвата целевой клиент не был подключён.
Результаты того захвата нельзя было относить к тестовому ПК. Ниже приведены
результаты повторной проверки после точного сопоставления адресов.

## Проверка NGFW без изменений

На `IDECO-SPB-PILOT` подтверждено:

- сам NGFW отвечает от `8.8.8.8` за `13–14 ms`, потерь нет;
- `ideco-agent-backend`, `ideco-agent-websocket` и
  `ideco-websocket-vpn-server@agent` активны;
- peer `10.128.0.4` с endpoint `10.76.40.83` имеет свежий handshake и входит в ipset
  `authorized_users`;
- маршрут из VPN namespace до `8.8.8.8` корректно ведёт через veth `main`;
- automatic MASQUERADE для `10.0.0.0/8` существует и срабатывает;
- conntrack содержит двустороннюю ICMP-сессию, SNAT
  `10.128.0.4 -> 172.31.146.2`;
- синхронный `tcpdump` показал для каждой последовательности полный цикл:
  `LagentWG_srv In` request → `Eeth4 Out` SNAT request → `Eeth4 In` reply →
  `LagentWG_srv Out` reply;
- счётчик WireGuard TX увеличивался во время ответов.

Пример подтвержденной последовательности для ICMP seq 134:

```text
LagentWG_srv In   10.128.0.4 > 8.8.8.8 echo request
Eeth4 Out         172.31.146.2 > 8.8.8.8 echo request
Eeth4 In          8.8.8.8 > 172.31.146.2 echo reply
LagentWG_srv Out  8.8.8.8 > 10.128.0.4 echo reply
LagentWG_srv In   10.128.0.4 > 8.8.8.8 ICMP protocol 1 unreachable
```

Последняя строка особенно важна: после доставки echo reply клиентский Windows
стек сам вернул сообщение `protocol 1 unreachable`. Также зафиксированы
двусторонние DNS-запросы и установленные HTTPS-сессии, но у отдельных TCP SYN
наблюдались повторные ответы до принятия клиентом. Это совместимо с локальным
WFP/NDIS-фильтром или конфликтом драйверов на Windows.

### Повторная проверка задержки

Во время непрерывного `ping -t 8.8.8.8` для последовательностей 244–267 NGFW
получал запросы раз в секунду и возвращал каждый ответ в `Lvpn0` через
`13.1–13.3 ms`. Потерь и секундной задержки внутри NGFW не было. Прямой ping
от шлюза VLAN `10.76.40.1` до физического адреса ПК `10.76.40.83` дал 20/20,
среднее `1.265 ms`, максимум `3.353 ms`; Wi-Fi/L2 также не создаёт задержку.

Сразу после подключения наблюдался крупный нисходящий burst: счётчик peer TX
вырос примерно на 106 MiB за 25 секунд; среди соединений был Microsoft
Delivery Optimization/Akamai. Позднее поток прекратился (около 8 KiB за пять
секунд). Он мог усиливать задержку в клиентской очереди, но не объясняет её,
если 3000 ms сохраняются после завершения загрузки.

## Вывод

NGFW, его маршрутизация, firewall, SNAT и серверный WireGuard data plane для
данной сессии исправны. Ответы передаются клиенту. Потеря после этого находится
на Windows-ПК: Ideco WinTun, WFP/NDIS-фильтр, endpoint security/DLP либо иной
локальный сетевой компонент. Наличие «Стахановца» является основной новой
гипотезой, но причинность ещё требует A/B-проверки.

Переход на TLS/443 можно использовать как диагностический A/B-тест: если TLS
на том же ПК работает, конфликт ограничен UDP/WireGuard-трактом. Он не нужен
для исправления NGFW SNAT, так как SNAT уже подтверждён.

## Повторное воспроизведение 2026-09-09: туннель «подключён», data plane отсутствует

В новом нерабочем состоянии тот же ПК имел physical IP `10.76.40.83`, VPN IP
`10.128.0.3`, endpoint UDP `49895`. В интерфейсе клиента соединение выглядело
установленным, но на NGFW:

- `latest handshake` оставался старым и за время замера не обновился;
- каждые примерно пять секунд приходил UDP/3051 пакет размером 148 байт;
- NGFW немедленно отвечал UDP/3051 пакетом размером 92 байта;
- это соответствует обмену WireGuard handshake initiation/response;
- клиент не завершал handshake, счётчики transfer почти не менялись;
- за 22 секунды в `LagentWG_srv`/`Lvpn0` не поступило ни одного внутреннего
  ICMP-пакета, несмотря на запущенный на Windows ping.

Следовательно, в состоянии тайм-аутов ping ещё не доходит до маршрутизации,
firewall или SNAT NGFW. Сервер отвечает на каждую попытку установки WireGuard,
но Windows-клиент не принимает/не обрабатывает ответ. Когда одна из повторных
попыток проходит, data plane появляется и ping начинает работать. Read-only
действия администратора на NGFW этот переход не вызывают; по времени они лишь
совпадали с автоматическими повторными попытками клиента.

Это уточняет основную гипотезу: локальный WFP/NDIS/DLP-фильтр периодически
отбрасывает входящие UDP/3051 ответы либо конфликтует с WireGuard-компонентом
Ideco. Контрольный переход только этого пользователя на Ideco Client TLS/443
является следующим наиболее информативным тестом.

## Временный A/B-тест TLS/443 — 2026-09-09 09:25 MSK

Активная сессия была идентифицирована журналом `ideco-vpn-authd` как локальный
пользователь `test4` (`test4@aurora-line.com`). Отдельного готового объекта
пользователя в правиле не было; единственное пилотное правило охватывает группу
`Net-Ideco-Pilot`. Поскольку активной была только эта тестовая сессия, в правиле
`/vpn-servers/access-rules/v5/records/1` временно заменён только протокол:

```json
"vpns": ["agent-vpn-ng"]
```

на:

```json
"vpns": ["agent-vpn-tls"]
```

Исходный JSON сохранён на NGFW:

`/var/lib/ideco-support/20260909-agent-vpn-tls-test/access-rule-1.before.json`

SHA-256 backup:
`69696c4a0d43917de411b9ee24f769d8767a0794fcd99bdbd4b92fbd56e52d94`.

После переподключения журнал подтвердил авторизацию `test4` с типом
`agent-vpn-tls`, в VPN namespace появился `tls0` и маршрут
`10.128.0.3 dev tls0`. При этом серверный websocket удаляет и вновь добавляет
клиента примерно каждые 15 секунд; `tls0` почти не передаёт данные, а 20
серверных ping до `10.128.0.3` дали 100% потерь. Итоговый результат на Windows
нужно сопоставить с этим временным состоянием.

Откат TLS-теста:

```bash
ETCDCTL_API=3 etcdctl --endpoints=http://127.0.0.1:2379 put \
  /vpn-servers/access-rules/v5/records/1 \
  "$(cat /var/lib/ideco-support/20260909-agent-vpn-tls-test/access-rule-1.before.json)"
```

После отката клиенту требуется переподключение.

## Изменения и откат

Конфигурация NGFW не менялась. Выполнялись только чтение таблиц, журналов,
conntrack, WireGuard-состояния и два ограниченных по ICMP захвата заголовков.
Откат не требуется.
