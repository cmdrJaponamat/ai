# Проверка native Service Desk API на тестовой PostgreSQL

Дата: 26.11.2026. Сервер: `spb-db` (`10.78.3.2`), БД: **только** `service_desk_sandbox`. Рабочие `portal_al`, `portal_correspondence`, HESK и будущая `service_desk` не менялись.

## Задача и исходное состояние

Нужно проверить первый read-only срез native API на настоящем PostgreSQL до разработки команд записи. До начала в `service_desk_sandbox` была только миграция `001_initial.sql`, 0 очередей и 0 заявок. Доступ по SSH `a.kuznetsov`, администрирование тестовой БД через `sudo -n -u postgres`.

## Изменения

- Применены `notes/projects/service-desk-multi-queue/migrations/002_stored_files.sql` и `003_api_runtime.sql` из репозитория `~/assistant`; обе транзакции завершились `COMMIT`.
- Для HTTP-интеграционного теста создана временная роль с правами только на `service_desk_sandbox` и SSH-туннель к локальному PostgreSQL. Секрет генерировался в памяти и не сохранялся. Роль, её права и туннель удалены после теста.
- Тест создавал синтетическую очередь, две заявки, публичное сообщение, внутреннюю заметку и файл. Первая версия очистки теста прервалась на отложенном ограничении «заявка требует заявителя»; остаток удалён в одной транзакции. Тест исправлен и повторён.

## Проверка

- `native-service-desk/integration.test.mjs` прошёл через HTTP и PostgreSQL 14: список, каталог, сводка, запрет чужой категории, сокрытие заметки и её файла от заявителя, доступ исполнителя к файлу.
- Финальный запрос: таблицы `stored_files`, `pending_uploads`, `report_queries` существуют; `queues=0`, `tickets=0`, временных ролей `sd_smoke_%=0`.
- Сервер native API в продуктиве не запущен, привязки очередей портала не менялись.

## Продолжение: проверка команд записи

В тот же день выполнен `native-service-desk/write.integration.test.mjs` через временную роль `sd_write_%` и SSH-туннель к **той же тестовой БД**. Проверены создание заявки, повтор с тем же ключом, конфликт при изменённом теле, ответ и статус в одной операции, заметка, назначение, самостоятельный переход, запрет заметки заявителю и два одновременных запроса с одной версией. Тест прошёл; после последней правки кода повторён успешно. Финально: `queues=0`, `tickets=0`, `idempotency_keys=0`, временных ролей `sd_write_%=0`. Рабочие БД, службы и привязки очередей не менялись.

## Откат и продолжение

Откат схемы не требуется: это выделенная пустая тестовая БД. Если нужно вернуться к состоянию до миграций, после проверки отсутствия подключений удалить **только** `service_desk_sandbox` и заново создать её с `001_initial.sql`; не выполнять это на рабочих БД. Следующее действие проекта — native-адаптер портала и команды записи, без переключения ИТ/Legal. Перезапуск и перезагрузка не требуются.
