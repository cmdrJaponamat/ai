# Veeam Exchange: диагностика долгого субботнего backup на SPB-NAS1

Дата: 2026-11-23, около 15:45 MSK. Проверка read-only; настройки NAS, Veeam и сети не менялись.

## Результат

`bkp_exchange_dag02` ежедневно стартует в 18:00. Обычные сессии 16–20.11 завершались за 7.0–7.3 ч. Субботняя сессия 21.11 длилась 40.1 ч и завершилась `Success` 23.11 в 10:09. Veeam настроен на субботнюю синтетическую полную копию (`SyntheticFullOptions.Enabled=True`, `Days=[6]`, weekly GFS). Чтение MX3 завершилось примерно за 2.4 ч, MX4 — за 4.6 ч; затем сборка двух полных `.vbk` по ~6.6 TB на NFS `/volume1/veeam-exchange` длилась более суток. Обе точки созданы успешно. Сессии 07.11 и 14.11 также длились около 39–41 ч и завершились ошибкой удаления старых `.vbk` по retention; точная причина этих ошибок отдельно не установлена.

В Zabbix хост `SPB-NAS1` (`10735`) опрашивается по SNMP. При проверке: `System Status=1`, RAID обоих томов `Status=1`, все 12 дисков `HealthStatus=1`, `/volume1` занято 50% (около 46.9/92.1 TB), CPU Idle около 61%. `/volume2` занято 93% и имеет отдельный открытый критический триггер, но NFS-репозиторий Veeam расположен на `/volume1`.

Ключевое наблюдение SNMP trends за этап синтетической копии 22.11 01:00 — 23.11 10:00: на `eth7` входило в среднем 833 Mb/s, на management `eth1` исходило 866 Mb/s, а исходящий поток на `eth7` был близок к нулю. CPU Idle в среднем 84%, загрузка дисков `/volume1` (`sda`–`sdh`) около 21–22%. Прямой read-only SNMP-запрос к NAS: маршрут по умолчанию `0.0.0.0/0` имеет next hop `10.78.0.254`, ifIndex 7 = `eth1`; `ifHighSpeed.7=1000` Mb/s. Специфического маршрута `10.78.20.0` в legacy ipRouteTable нет. Veeam gateway `AL-VEEAM` имеет адрес `10.78.20.99`; NFS endpoint NAS — `10.78.7.10` на `eth7`.

Вывод: ответы NFS клиенту Veeam идут через management `eth1` с физическим пределом 1 Gb/s, хотя запросы приходят на сервисный `eth7`. Эта асимметрия объясняет наблюдаемый предел сетевого потока и является вероятной главной причиной длительной синтетической сборки. Прямая причина ошибок retention 07/14.11 пока не доказана. Это расходится с задокументированной 29.09 схемой, где default route NAS должен был быть `10.78.7.254 dev eth7`.

## Следующее действие

Проверено read-only 23.11: AL-OBIT содержит активный адресный список `Admin-VPN=10.78.90.32/27` и разрешающее forward-правило для него. Административная машина текущей сессии имеет `10.78.90.34`; connection tracking показал её соединения с `10.78.0.250`. Zabbix-хост `SPB-NAS1` (`10735`) использует SNMP-интерфейс `10.78.0.250`; источник Zabbix — `10.78.3.251`, прямой опрос подтверждён прежним recovery и свежими метриками.

| Источник | Роль | Маршрут NAS после смены default gateway |
| --- | --- | --- |
| `10.78.0.0/24` | Локальная management VLAN1000 NAS `eth1=10.78.0.250` | Connected route через eth1; отдельный static route не нужен |

Это список **подтверждённых** удалённых источников, а не исчерпывающий аудит всех прошлых подключений DSM. Перед изменением маршрута ещё раз сверить действующие сессии/журналы DSM, router connection tracking и доступ администратора из другого адреса. Не маршрутизировать через eth1 всю `10.78.3.0/24` или всю security-management `10.78.20.96/27`: подтверждён только Zabbix `/32`, а Veeam `10.78.20.99` должен отвечать через eth7. PVE/PBS `10.78.2.0/24` используют storage/service-адреса NAS, не подтверждены как клиенты DSM-management и потому не требуют маршрута через eth1.

## Проектные сети, заложенные в схему

| Сеть | Роль в целевой схеме | Правило для NAS |
| --- | --- | --- |
| `10.251.0.0/26` | Будущий `VPN-ADMINS`, замена действующего `10.78.90.32/27` | Разрешить доступ к management-адресу `10.78.0.250`; при переходе обеспечить ответ через eth1, старый пул сохранять до завершения миграции |
| `10.78.20.96/27` | `DC-SECURITY-MGMT`: Veeam, Zabbix, Oxidized и другие security-сервисы | Не задавать для всего `/27` маршрут через eth1; Veeam `10.78.20.99` должен ходить к NFS по eth7. Для будущих узлов мониторинга добавлять адреса `/32` после назначения IP и выбора management endpoint |
| `10.78.2.0/24` | `DC-HYPERVISOR`: PVE/PBS | Не считать автоматически источником управления DSM; service/storage-потоки к NAS остаются на своих интерфейсах. Административный jump host, если появится, учитывать по фактическому адресу |

Обычный статический маршрут на NAS выбирается **по удалённому адресу** и направит через eth1 весь трафик к этому клиенту, даже если он обратился к `10.78.7.10`. Для устойчивой целевой схемы «management-адрес через eth1, сервисный адрес через eth7» следует оценить source-based routing/`Enable Multiple Gateway` в DSM и проверить фактическую таблицу правил на текущей версии, либо сохранить узкие маршруты только к реальным management-клиентам. Будущие подсети не активировать заранее. Проектный wiki-runbook Synology пока указывает DSM/SNMP на сервисный `10.78.7.10` и тестирует bond, который уже разобран; перед внедрением синхронизировать его с принятой схемой отдельного management-адреса `10.78.0.250`.

## Согласованная целевая таблица маршрутов SPB-NAS1

Эта таблица описывает **целевое**, а не уже применённое состояние. Все адреса и префиксы ниже относятся к IPv4. Выбор маршрута выполняется по **адресу назначения ответа NAS**; имя службы, адрес назначения входящего запроса и тип трафика сами по себе маршрут не выбирают.

| Адрес назначения ответа NAS | Маршрут | Условие |
| --- | --- | --- |
| `10.78.0.0/24` | Подключённая сеть `eth1`, адрес NAS `10.78.0.250/24`; шлюз не нужен | Постоянно |
| `10.78.5.0/24` | Подключённая сеть `eth4`, адрес NAS `10.78.5.10/24`; шлюз не нужен | Постоянно, сеть хранения/iSCSI |
| `10.78.7.0/24` | Подключённая сеть `eth7`, адрес NAS `10.78.7.10/24`; шлюз не нужен | Постоянно, сервисная сеть/NFS |
| `10.78.90.32/27` | Статический маршрут через `10.78.0.254`, интерфейс `eth1` | Действующий пул Admin VPN; сохранять до окончания его использования |
| `10.78.3.251/32` | Статический маршрут через `10.78.0.254`, интерфейс `eth1` | Действующий сервер Zabbix, опрашивает `10.78.0.250` |
| `10.251.0.0/26` | Статический маршрут через `10.78.0.254`, интерфейс `eth1` | Добавить **только при вводе** нового пула VPN-ADMINS; до этого маршрут не создавать |
| Все прочие IPv4-адреса | Единственный маршрут по умолчанию `0.0.0.0/0` через `10.78.7.254`, интерфейс `eth7` | В том числе Veeam `10.78.20.99`, worker Veeam `10.78.20.100` и остальные адреса `10.78.20.96/27`, если не появится отдельное обоснованное исключение |

Не добавлять маршрут `10.78.90.0/24`: подтверждённый действующий VPN-пул — именно `10.78.90.32/27`. Не направлять целиком `10.78.3.0/24` или `10.78.20.96/27` через `eth1`. На `eth4` не назначать шлюз по умолчанию; сеть хранения `10.78.5.0/24` обслуживается подключённым маршрутом.

Статические маршруты через `eth1` распространяются на **все** ответы NAS соответствующим адресам, в том числе на обращения этих клиентов к `10.78.7.10` или `10.78.5.10`. Если требуется строго выбирать выходной интерфейс по исходному адресу NAS, это отдельная настройка policy routing, а не свойство приведённой таблицы. Перед применением проверить фактические маршруты DSM, доступность DSM из Admin VPN, SNMP с Zabbix и путь NFS к Veeam; подготовить откат к текущему default gateway `10.78.0.254` на `eth1`.
