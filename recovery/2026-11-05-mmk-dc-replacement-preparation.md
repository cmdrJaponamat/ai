# Замена DC2 в Мурманске: подготовка MMK-DC1-AL

Дата: 2026-11-05. Площадка: Мурманск, Тарана 25. Система: `aurora-logistics.local`.

## Задача и подтверждённый контекст

- Пользователь готовит Windows Server 2019 в СПб на `192.168.203.40` для перевозки на Тарана. Постоянное имя: `MMK-DC1-AL`. После вывода старого DC2 желаемый адрес: `10.10.20.50`. На переходное время выбран `10.10.20.51`.
- По решению пользователя DC и сервер печати будут размещены в одной Windows Server 2019. Microsoft рекомендует выключать Print Spooler на DC; совместное размещение принимается как эксплуатационный риск и требует ограничений доступа и драйверов.
- `SITE-MMK` уже существует. `DC2` (`10.10.20.50`, Windows Server 2019 Standard) находится в нём, является writable GC. `SPB-DC1-AL` (`10.78.3.50`) находится в `SITE-SPB-DC`. Все пять FSMO-ролей находятся на SPB-DC1-AL.
- `10.10.0.0/16`, `10.11.0.0/16`, `10.12.0.0/16`, `10.13.0.0/16`, `10.17.0.0/16` и `192.168.103.0/24` привязаны к `SITE-MMK`. Сеть текущего расположения `192.168.203.0/24` привязана к `SITE-SPB-MILLION`.
- `SL-AD-TRANSITION` соединяет `SITE-MMK` и `SITE-SPB-DC` с интервалом 15 минут. Домен и лес имеют уровень Windows Server 2016, миграция SYSVOL на DFSR завершена. `repadmin /replsummary` с SPB-DC1-AL: 0 ошибок в доступном направлении; известный удалённый опрос DC2 возвращает 110 из этой SSH-сессии.
- Локальная адресация Тарана: серверный VLAN 20 `10.10.20.0/24`, шлюз `10.10.20.1`. Целевая сегментация предусматривает отдельные сети для принтеров и print-node, но на Тарана они ещё не подтверждены как введённые.
- Имя `MMK-DC1-AL` отсутствовало в AD и DNS на момент проверки. DHCP сети `10.10.30.0/24` на `AL-MMK` прямо выдаёт DNS `10.10.20.50`; это подтверждает необходимость контролируемого возврата адреса `.50` новому DC. Сам шлюз использует DNS `10.78.4.253`.
- В `OU=Domain Controllers` прямо связана `Default Domain Controllers Policy`; отчёты действующих GPO не содержат настройки `Spooler`. Это не отменяет риска размещения Print Spooler на DC.

## Резерв временного IP: выполненное изменение на AL-MMK

- Перед изменением на `AL-MMK` (`10.10.30.1`) прочитан DHCP-пул `vlan20DHCP`: `10.10.20.3-10.10.20.60`. Сервер DHCP работает на `vlan20(SERVERS)`. Для `.51` нет lease и PTR; с DC1 ping не отвечает, на шлюзе ARP `status=failed`. Это не абсолютное доказательство отсутствия выключенного статического узла.
- Перед правкой на шлюзе сохранён `/ip pool export` в `mmk-dc1-pool-before-20261105.rsc` (2026-11-05 17:27:48 MSK). Пул `vlan20DHCP` изменён на `10.10.20.3-10.10.20.50,10.10.20.52-10.10.20.60`, исключив `.51`. Повторное чтение подтверждает новое значение, DHCP-сервер `vlan20DHCP` включён, lease `.51` отсутствует. До назначения IP новому серверу повторно проверить ARP, leases и локальную инвентаризацию.
- Откат: только после снятия `.51` с нового сервера либо выбора иного временного IP выполнить на `AL-MMK` `/ip pool set [find where name="vlan20DHCP"] ranges=10.10.20.3-10.10.20.60`. Прочие DHCP-пулы и маршрутизацию не менять.

## Граница подготовки

- Пока новый сервер находится в СПб, оставить текущий IP `192.168.203.40`; можно переименовать, обновить ОС, проверить оборудование, подключить к домену как member server и подготовить средства резервного копирования.
- Уточнение 2026-11-06: повышение на `192.168.203.40` в `SITE-SPB-MILLION` технически возможно, но для этой замены **отклонено**: DC опубликует записи поиска, и клиенты СПб смогут начать его использовать. Выбран сценарий подготовки member server в СПб и удалённого повышения в DC после подключения на Тарана.
- Для развёртывания без выезда администратора после проверки доменного членства и RMM в СПб статический `.51` задать последним действием перед штатным выключением. В офисе местный сотрудник только подключает сервер к проверенному порту VLAN 20 и включает его; повышение в DC, проверки и смена адреса на `.50` выполняются удалённо. Сеть `10.10.20.0/24` в СПб для этого разворачивать не требуется.
- `DC2` сейчас не выключать ради подготовки: `.50` выдаётся как DNS клиентам VLAN 30, а новый DC на этом адресе одновременно со старым работать не может. Преждевременный вывод `.50` создаёт окно недоступности DNS и локального DC на время перевозки.
- Адрес `.50` назначать новому DC только после штатной демоции DC2, отключения его интерфейса и проверки отсутствия конфликта IP.
- Пошаговые команды для консоли нового сервера и контролируемой замены: [`../scripts/README-mmk-dc1-al-replacement.md`](../scripts/README-mmk-dc1-al-replacement.md).

## Проверка, откат и перезапуски

- Проверка DHCP-резерва: перечитать пул на AL-MMK, убедиться, что `.51` отсутствует в диапазоне выдачи, остальные диапазоны сохранены.
- Для изменения пула перезагрузка маршрутизатора, сервера и клиентов не требуется. Для переименования, вступления в домен, промоции и демоции DC перезагрузка потребуется на соответствующих Windows Server.
- На 2026-11-05 подготовка нового сервера и вывод DC2 ещё не выполнялись; текущий статус приведён ниже.

## 2026-11-20: сервер включён на Тарана с DHCP-адресом `.3`

- Пользователь сообщил адрес `10.10.20.3`. Проверка на `AL-MMK`: динамическая DHCP-аренда `.3` в `vlan20DHCP`, `host-name=MMK-DC1-AL`, MAC `FC:9D:05:7E:AD:7F`, ARP reachable на `vlan20(SERVERS)`. Пул по-прежнему `10.10.20.3-10.10.20.50,10.10.20.52-10.10.20.60`; для `.51` аренды нет, ARP failed. С рабочего ПК на `.3` отвечают TCP 135/445/3389, а на `.50` отвечают DNS/Kerberos/LDAP/SMB/RDP.
- DNS `MMK-DC1-AL.aurora-logistics.local` на DC2 и SPB-DC1-AL сейчас возвращает `.3`. Одновременно `file.aurora-logistics.local` возвращает `.3`, а PTR `.3` содержит `nas2` и `file`; принадлежность этих старых записей нужно проверить отдельно. Не удалять их вслепую.
- С `SPB-DC1-AL` объект компьютера `MMK-DC1-AL` существует и включён. `repadmin /replsummary` показывает 0/5 ошибок для доступного направления `DC2` → `SPB-DC1-AL`, но удалённый опрос DC2 из этой сессии вернул 110. На новом сервере признаки работающего DC пока не обнаружены (TCP 53/88/389 закрыты).
- Следующий шаг: на консоли нового сервера перевести интерфейс с DHCP `.3` на статический `10.10.20.51/24`, шлюз `10.10.20.1`, DNS `10.10.20.50`, `10.78.3.50`; сеанс RDP на `.3` оборвётся. Проверить доступ на `.51`, регистрацию DNS, `nltest /dsgetsite` = `SITE-MMK`, связь с DC2 и ЦОД, затем здоровье/резервную копию DC2. Только после этого повышать новый сервер в DC по runbook. Старый DC2 оставлять работающим.
- Изменений сети, DHCP, DNS и AD в ходе этой диагностики не выполнялось. Откат не нужен; перезагрузка не требовалась.

## 2026-11-20: временный статический адрес `.51` назначен

- Пользователь выполнил `ipconfig /registerdns`. На `MMK-DC1-AL`: `nltest /dsgetsite` = `SITE-MMK`; `Test-NetConnection 10.10.20.50 -Port 389` = True с исходного `10.10.20.51`; `Resolve-DnsName` через DC2 показал A `.51`. В одном выводе была AAAA `fe80::...`; повторный прямой запрос к DC2 AAAA её уже не показал.
- С рабочего ПК `.51` доступен по TCP 135/445/3389. На `AL-MMK` ARP `.51` reachable с MAC `FC:9D:05:7E:AD:7F`, DHCP-аренды `.51` и прежней `.3` нет. На DC2 прямая A-запись и PTR `.51` указывают `MMK-DC1-AL`. На SPB-DC1-AL прямая A-запись пока NXDOMAIN: ждать репликации DNS между сайтами и проверить повторно.
- `repadmin /showrepl SPB-DC1-AL` показывает успешное получение от `DC2` всех пяти разделов AD в 10:59:46 MSK. Проверка `dcdiag /s:DC2` из SSH-сессии на SPB-DC1-AL сообщила `Access denied` при привязке к каталогу и не заменяет локальную проверку DC2. С SPB-DC1-AL к новому серверу доступны TCP 135/445/3389.
- Следующий шаг: подтвердить на новом сервере DHCP=No, DNS `.50` и `10.78.3.50`, время, доверие к домену и доступ к DC1; на DC2 проверить `dcdiag`, `repadmin` и актуальную резервную копию System State. Затем повысить `MMK-DC1-AL` в `SITE-MMK` как дополнительный writable GC/DNS с источником `DC2`. Старый DC2 до проверки нового не выводить.
- Эти действия были только чтением; на DNS/AD/роутере изменений ассистентом не сделано. Откат не нужен; перезагрузка не требовалась.

## 2026-11-20: защита адресов `.3` и `.50` в DHCP-пуле

- Перед изменением проверено: текущий `vlan20DHCP` = `10.10.20.3-10.10.20.50,10.10.20.52-10.10.20.60`; DHCP-аренд `.3` и `.50` нет. ARP `.3` failed после перехода нового сервера на `.51`, ARP `.50` reachable у работающего DC2. DNS `file.aurora-logistics.local` по-прежнему указывает `.3`.
- Выполнено: на `AL-MMK` сохранён экспорт `/ip pool` в `mmk-dc1-pool-before-20261120.rsc`, затем `vlan20DHCP` установлен в `10.10.20.4-10.10.20.49,10.10.20.52-10.10.20.60`. Повторное чтение подтвердило значение. `.3`, `.50` и `.51` теперь не выдаются по DHCP; `.3` исключён до выяснения старой записи `file`.
- После изменения TCP 53/389 на DC2 и 135/445/3389 на новом сервере доступны; DNS DC2 возвращает `.51` для `MMK-DC1-AL`. Перезагрузка роутера, DC и клиентов не требовалась.
- Откат только при подтверждении, что `.3` и `.50` свободны для DHCP: `/ip pool set [find where name="vlan20DHCP"] ranges=10.10.20.3-10.10.20.50,10.10.20.52-10.10.20.60`. Возврат `.50` в пул во время работы DC недопустим. Перезагрузка роутера и клиентов не требуется.
