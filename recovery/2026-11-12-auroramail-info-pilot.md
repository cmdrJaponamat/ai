# Пилот входящей корреспонденции `info` в PortalAL

Дата: 2026-11-12. Владелец разрешил перейти от проектирования к реализации и использовать первый запуск и исправления заказчика как проверку критериев.

## Состояние

- PortalAL содержит отдельный модуль `server/correspondence/` для очереди `info`: чтение IMAP через `EXAMINE`/`BODY.PEEK[]`, извлечение фактов и вложений, локальное OCR, карточки в PostgreSQL, рекомендации по редакции правил, фиксация решений и расхождений. ИТ и юридические HESK не менялись.
- В портале добавлены «Входящая корреспонденция» (`/info/correspondence`) и «Настройки очередей → info → Правила». Полные письма постоянно в БД не хранятся; оригинал скачивается из IMAP по UID и текущему UIDVALIDITY.
- На сервере PortalAL `10.78.3.149` в `/opt/portal-al/.env` добавлен `PORTAL_INFO_GROUP_DN=CN=App-Portal-Info-Operators,OU=Applications,OU=CompanyGroups,DC=aurora-logistics,DC=local`. Копия прежнего файла: `/opt/portal-al/.env.before-info-20261112`. Группа существует в AD. Администраторы также видят очередь.
- Первый приём включён с `UIDVALIDITY=14`, `last_uid=128597`; старый архив не импортирован. Два следующих письма создали карточки `128598` и `128599`, повторный опрос создал 0 дубликатов. Письмо с файлом `.p7s` повторно разобрано после исправления классификации подписи, история изменения сохранена. Исходный счёт на оплату дал слишком уверенную регистрацию; через черновик и предпросмотр опубликована редакция правил 2 с ручным разбором счетов. Код для этой правки критериев не собирался повторно после публикации правила.
- Исходящие письма из портала и запись номера 1С в этом пилоте ещё не реализованы; решение оператора в карточке не выполняет внешнее действие. Это явно показано в интерфейсе.

## Проверка

- Локально: `npm test` (22 теста), `npm run build`, синтаксис Python/Node. В рабочем контейнере прочитаны пять исторических писем, включая PDF, DOCX, OCR и отдельную подпись. Содержимое/секреты в логи или Git не помещались.
- Производственный образ `477b88f` healthy; `curl http://127.0.0.1:5180/api/health` отвечает HTTP 200, `/info/correspondence` отвечает HTTP 200. CI/CD run `43263840848` завершился успешно. Обе существующие очереди HESK (`it`, `legal`) после развёртывания доступны.
- Источник в таблице `portal_correspondence_sources` остаётся включённым, ошибка очищена. Если появится ошибка обработки, курсор не продвигается за проблемное письмо. Последний подтверждённый успешный курсор после первых двух писем: `128599`. Карточка `128598` после пересчёта по редакции 2 имеет маршрут «ручной разбор»; `128599` сохранила «регистрация» и редакцию 1 до новой обработки.

## Откат и эксплуатация

1. Для остановки приёма нажать «Приостановить» в очереди. Это не изменяет сообщения в Exchange.
2. Для отката приложения использовать предыдущий образ PortalAL через стандартный `deploy/deploy-image.sh` или `docker compose` с прежним `PORTAL_IMAGE`. Таблицы карточек/правил останутся в PostgreSQL и не влияют на HESK.
3. Изменение `.env` можно удалить, восстановив только строку `PORTAL_INFO_GROUP_DN`, после чего пересоздать контейнер. Полный откат к `/opt/portal-al/.env.before-info-20261112` допустим лишь после сверки последующих изменений `.env` и ключа шифрования IMAP.
4. Новые правила публикуются через черновик в портале. Для письма с уже сохранённой рекомендацией администратор использует «Разобрать повторно» до принятия решения; прежнее предложение остаётся в аудите.

Перезапуск: контейнер PortalAL пересоздавался для новой переменной окружения и при CI/CD. Пользователям с открытой сессией может потребоваться повторный вход, чтобы роль `info` появилась в сессии. Перезагрузка сервера не нужна.
