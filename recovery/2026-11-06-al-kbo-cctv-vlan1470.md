# AL-KBO: подготовка единого VLAN видеонаблюдения

Дата: 2026-11-06. Статус: VLAN и DHCP подготовлены; `ether2` переведён в VLAN 1470. Регистратор пока на legacy IP, его DHCP-переход ожидается.

## Задача

Камеры и регистратор подключены к одному неуправляемому коммутатору на `ether2` AL-KBO. Вместо двух целевых зон используется один access VLAN `1470` для обоих типов устройств. На текущем этапе адреса устройств сохраняются.

- AL-KBO: hAP ac². Oxidized опросил его успешно 2026-11-06; последняя перемена конфигурации в snapshot датирована 2026-10-23.
- `BRIDGE-LOCAL` работает с `vlan-filtering=yes`. Существуют VLAN `1400` (пользователи) и `1450` (гости).
- `ether2` не входит в bridge. На нём адрес `192.168.1.254/24`; srcnat в этот порт и dstnat `10.10.3.4:80` на `192.168.1.2:80` действуют. Роль устройства `.2` отдельно не подтверждена.
- Целевая адресная схема КБО: VLAN `1470`, `10.12.47.0/24`, шлюз `10.12.47.1`. Роль VLAN `1480` для NVR в этой физической схеме не применяется.

## Откат и границы

- Для подготовительного шага: удалить новые объекты в обратном порядке: `/ip dhcp-server remove [find where name=dhcp-cctv-cameras]`; `/ip dhcp-server network remove [find where comment=SITE-CCTV-PREP]`; `/ip pool remove [find where name=pool-cctv-cameras]`; `/ip address remove [find where interface=vlan1470-cctv and comment=SITE-CCTV-PREP]`; `/interface bridge vlan remove [find where vlan-ids=1470]`; `/interface vlan remove [find where name=vlan1470-cctv]`. Перед каждым удалением сверить результат `print`; не использовать фильтр `address=.../24` для поиска объекта.
- Для переключения `ether2`: вернуть его из bridge, восстановить `192.168.1.254/24` непосредственно на порт и предыдущую запись bridge VLAN. Требуется независимый административный доступ и сохранённый backup.
- Камеры и NVR в одном L2: RouterOS не сможет фильтровать трафик между ними. Межзоновая изоляция относится только к маршрутизируемому трафику.

После проверки нового IP сменить dstnat `10.10.3.4:80` с `192.168.1.2` на `10.12.47.2` и повторить HTTP-проверку. Предсменный экспорт с правами `0600`: `/home/admin-al/ansible_al/artifacts/mikrotik/production/al-kbo-20261106-pre-vlan1470/al-kbo-pre-ether2-cutover.rsc`, SHA-256 `ff02e9513d46f135e0566748dd2b01cc301afad2c1a45c5b3ad0037db0ca990a`.

Порядок:

1. Создать статическую DHCP lease `10.12.47.2` для MAC регистратора вне динамического пула `.50-.250`.
2. Добавить `ether2` как untagged в bridge VLAN 1470 и bridge port с `pvid=1470`, `ingress-filtering=yes`, `frame-types=admit-only-untagged-and-priority-tagged`. Интерфейс управления `10.10.3.4` работает через OVPN/ether1 и не зависит от этого порта.
3. Перенести только старый адрес `192.168.1.254/24` с `ether2` на `vlan1470-cctv` как временный вторичный адрес. Не удалять его до подтверждения всех устройств на новых адресах.
4. Дождаться DHCP lease регистратора `10.12.47.2`, проверить ping/HTTP, затем сменить только `to-addresses` существующего dstnat `10.10.3.4:80` на `10.12.47.2`. Проверить HTTP 200 через прежний адрес доступа.
5. Проверить остальные leases, доступ к AL-KBO по `10.10.3.4` и `10.12.40.1`, наличие старого IP на VLAN и отсутствие разрыва роутера.

Так как устройства уже настроены на DHCP, откат L2 сам по себе не вернёт им старые адреса: при отсутствии новых leases сначала диагностировать DHCP и при необходимости согласовать локальное восстановление адресов устройств.

### Фактическое переключение

- Создана статическая DHCP lease `10.12.47.2` для MAC регистратора `08:54:11:AC:BB:74`, пока `waiting`.
- `ether2` добавлен в `BRIDGE-LOCAL` как untagged/access VLAN 1470 с `pvid=1470`, `ingress-filtering=yes` и `frame-types=admit-only-untagged-and-priority-tagged`.
- Старый шлюз `192.168.1.254/24` перенесён с `ether2` на `vlan1470-cctv` как временный вторичный адрес рядом с `10.12.47.1/24`.
- Старое forward-правило `accept out-interface=ether2` стало invalid после включения порта в bridge. Его `out-interface` заменён на `vlan1470-cctv`, сохранив прежнее направление доступа.
- Старое srcnat masquerade `out-interface=ether2` также стало invalid. Из-за этого dstnat к регистратору доходил без ответов. `out-interface` srcnat заменён на `vlan1470-cctv`; старый dstnat на `192.168.1.2:80` не менялся.
- После исправления srcnat прежний адрес просмотра `http://10.10.3.4/` снова возвращает HTTP 200.
- Появилась первая DHCP-аренда `10.12.47.250` для MAC `DC:07:F8:B7:23:F9`. Регистратор всё ещё отвечает на `192.168.1.2` и не отправлял DHCP-запрос; static lease `.2` ожидает клиента. Один клиент `.250` пытается подключиться к старому адресу регистратора `192.168.1.2:8000`.
- После обновления srcnat соединения `10.12.47.250 → 192.168.1.2:8000` имеют ответные пакеты; связность камеры с NVR через временную маршрутизацию подтверждена на уровне TCP.
- Постсменный экспорт с legacy-адресом регистратора: `al-kbo-post-ether2-cutover-nvr-legacy.rsc` в каталоге backup, SHA-256 `0e28ee14d594cec8fc192599184333846682e7587beb94860626257895666c32`, права `0600`.

### Дополнение к откату

Перед возвратом `ether2` из bridge вернуть out-interface исходных forward-accept и srcnat-masquerade правил с `vlan1470-cctv` на `ether2`; после возврата проверить, что правила валидны. Static DHCP lease `.2` можно оставить до завершения миграции или удалить по MAC, если миграция отменена. Старый dstnat пока остаётся на `192.168.1.2`.
