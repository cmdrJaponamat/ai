# План перевода виртуальных машин на целевую сегментацию ЦОДа

Дата: 2026-09-07. Статус: план; production-конфигурация этим документом не
изменялась.

## 1. Цель и исходное состояние

Перевести ВМ кластера `SPB-OBIT-DC` из общей нетегированной сети в ролевые
VLAN, определённые согласованной матрицей сегментации, с межзоновой политикой
`deny by default` и явно разрешёнными потоками.

К началу работ уже готов L2-транспорт VLAN
`1000,1020,1030,1070,1100,1200-1207,1210,1220-1221,1230,1240` через AL-OBIT,
оба H3C и `vmbr0` PVE1-PVE3. iSCSI `1040/1050` и Corosync `1060/1061`
остаются на выделенных физических интерфейсах и в миграцию ВМ не входят.

Сейчас большинство production-подсетей назначено непосредственно общему
нетегированному `bridge` AL-OBIT. Поэтому нельзя просто менять тег отдельной
ВМ: одинаковый IP-префикс не должен одновременно существовать в двух
изолированных L2-доменах. Переключение выполняется атомарными группами по
IP-префиксу, а не произвольными отдельными ВМ.

## 4. Обязательная подготовка до первого production-переключения

1. Снять полный read-only snapshot фактического состояния:
   конфигурации VM NIC, IP/маршруты/DNS внутри гостей, RouterOS IP/route/NAT/
   firewall/address-list, DNS-записи, сертификаты, публикации reverse proxy,
   Exchange connectors/DAG, backup/monitoring jobs. Не считать ARP полным
   источником инвентаризации.
2. Выяснить отсутствующие адреса VM123 и VM130, роль второго NIC VM124 и
   точное назначение `spb-vpn-srv`/10.78.4.253.
3. Убедиться, что VM111 не оставлена в Exchange maintenance после работ с
   Synology. До любой сетевой миграции DAG добиться `Mounted/Healthy`, снять
   `ServerWideOffline`, activation block и cluster pause в штатном порядке.
4. Утвердить адресный лист новых IP. Зарезервировать адреса и проверить
   конфликты ARP/ping. Особенно:
   - новый IP KSC, освобождающий 10.78.20.97 под шлюз VLAN1202;
   - новые адреса Directum, Licensing1C/1C, WTS;
   - адреса всех ВМ, уходящих из 10.78.3.0/24 в DMZ/APP/DB/SECURITY.
5. Составить матрицу потоков `source zone/host → destination zone/host →
   protocol/port → owner`. Источники: firewall counters, active connections,
   конфиги приложений и владельцы. Не переносить зону только с временным
   `allow any`.
6. На AL-OBIT подготовить для каждой зоны отключённый/безадресный VLAN SVI,
   address-list и disabled firewall rules. Не назначать на SVI адрес подсети,
   пока такой же префикс остаётся на legacy bridge.
7. Для новых подсетей (DMZ 10.78.10.0/27, DB 10.78.20.160/28, VPN
   10.78.20.68/30) SVI можно создать и проверить заранее, если подтверждено
   отсутствие пересечений и настроены ACL. Для существующих префиксов шлюз
   переносится атомарно в окне.
8. Создать резервные копии AL-OBIT, H3C startup config и конфигураций PVE;
   обеспечить независимый доступ через WAN/BMC. Временный WAN-доступ должен
   иметь актуальный динамический адрес, ограниченный source allow-list и срок.
9. На каждой ВМ подготовить локальный rollback: текущие IP/mask/gateway/DNS,
   VLAN tag, firewall profile; для Windows — доступ через QGA/console, для
   Linux — QGA/SSH и сохранённый сетевой конфиг.
10. Снизить DNS TTL изменяемых записей минимум за один прежний TTL до окна.
    Не менять MAC без необходимости, чтобы сохранить лицензии и привязки.

## 5. Механика одного окна

Для нового, не пересекающегося префикса допускается перенос одной ВМ. Для
префикса, уже находящегося на legacy bridge, единицей переключения является
вся группа этого префикса.

1. Зафиксировать baseline: PVE quorum/HA/storage, состояние сервиса, DNS,
   доступ пользователей, NAT counters и зависимые подключения.
2. Сделать свежий backup/export конфигурации шлюза и записать команды точного
   обратного изменения. Snapshot ВМ не использовать как единственный backup,
   особенно для Exchange/БД.
3. Остановить либо перевести сервис в maintenance. Для кластера/репликации
   сначала перенести активную роль на незатрагиваемый узел.
4. Для старого префикса одним change-set:
   - отключить/перенести IP-шлюз с legacy bridge на целевой VLAN SVI;
   - включить заранее подготовленные ACL/NAT;
   - назначить всем ВМ группы целевые tag/IP/mask/gateway/DNS;
   - обновить DNS, NAT, address-list, monitoring и backup definitions.
5. Очистить только относящиеся к изменённым адресам ARP/conntrack/DNS caches,
   если это необходимо; не очищать таблицы целиком.
6. Проверить с самой ВМ: шлюз, DNS/NTP/AD, необходимые upstream; затем с
   разрешённых клиентских зон; затем убедиться, что запрещённые зоны доступа
   не получили.
7. Наблюдать counters/logs не менее 30 минут для обычного сервиса и не менее
   полного рабочего цикла для почты, backup, VPN и бизнес-приложений.
8. Критерий отката: недоступен шлюз/AD/DNS, потеряна критичная зависимость,
   необъяснимый deny, деградация кластера/репликации либо нет независимого
   пути администрирования. Откатить всю атомарную группу, включая шлюз, ACL,
   NAT, DNS и VM tag/IP; частичный откат запрещён.

## 6. Рекомендуемый порядок волн

### Волна 0 — инфраструктурный пилот

- Проверить каждую SVI через VM107, не меняя production.
- Проверить маршрутизацию, MTU, DNS/NTP, admin VPN и default deny.
- Перенести VM100 PBS в VLAN1020 отдельным окном; адрес и шлюз остаются.
  PVE-host management в VLAN1020 не смешивать с миграцией ВМ и выполнять
  отдельным проектом через iLO/Corosync fallback.

### Волна 1 — зоны с новым префиксом или простой изолированной ролью

1. VLAN1204: VM118 DB — только после готовности allow-list клиентов.
2. VLAN1100: по одной VM112/125/129/130 после подтверждения ролей,
   публикаций и новых IP.
3. VLAN1203: VM139 (префикс 10.78.20.128/28 целиком).
4. VLAN1206: VM128 и, после подтверждения, VM138.

### Волна 2 — управление безопасностью и приложения

1. Сначала перенумеровать VM113 KSC с 10.78.20.97, обновить агентов/DNS и
   подтвердить, что старый адрес более не используется.
2. Атомарно перенести префикс 10.78.20.96/27 на VLAN1202 и целевые
   VM103/105/113/127/131/133/134/192 с новыми адресами.
3. Атомарно перенести 10.78.20.32/27 на VLAN1200: VM122/123/132 и другие
   выявленные сервисы этого диапазона. Шлюз меняется с текущего .62 на .33.

### Волна 3 — UC и бизнес-сегменты с перенумерацией

1. VLAN1205: VM114 и VM124; проверить SIP/RTP, NAT, телефонию и второй NIC.
2. VLAN1210: VM116 с новым адресом в /29; обновить DNS, интеграции и клиентов.
3. VLAN1220/1221: сначала назначить новые адреса VM119/121 и VM137, затем
   разделить бывшую общую /24 на две зоны. VM120 может сохранить .3, но
   получает /28 и шлюз .1. Проверить RDS→1C→DB и лицензирование.
4. VLAN1201: VM126 только после отдельного исследования роли и маршрутов VPN;
   перенос затрагивает маршрутизацию клиентских пулов и выполняется как
   отдельное сетевое окно.

### Волна 4 — tenant-зоны

- VLAN1230: атомарно VM104/106/109; сохранить адреса и шлюз .254, проверить
  AD/DNS, Exchange и witness.
- VLAN1240: атомарно VM110/150/151; сохранить адреса и шлюз .254, проверить
  tenant AD/DNS, Exchange и witness.

### Волна 5 — core services, последней

Префикс 10.78.3.0/24 переносится только после того, как из него уже вынесены
DMZ, APP, DB, SECURITY, RDS и прочие роли. Состав финальной группы должен быть
повторно получен из ARP/MAC/QGA непосредственно перед окном.

1. Проверить здоровье AD/DNS и DAG, наличие консольного доступа к обеим ВМ
   Exchange и актуальный backup System State/Exchange.
2. Сначала мигрировать неактивный DAG-член VM111, проверить replication и
   выполнить controlled switchover тестовой БД/копии.
3. Перенести DC/DNS VM102 и все оставшиеся core-сервисы атомарно со шлюзом
   10.78.3.254 на VLAN1030.
4. Последней перенести VM117: перед окном активировать БД на VM111, после
   переноса вернуть желаемое распределение и проверить очереди/копии.
5. Удалять 10.78.3.0/24 с legacy bridge только после подтверждения, что там
   не осталось MAC/IP и статических зависимостей.

## 7. Проверки после каждой волны

- PVE: quorum 3/3, Corosync links 0/1/2, HA без ошибок, все storage active.
- L2: MAC ВМ появляется только в целевом VLAN и на ожидаемом uplink; VLAN1 не
  изучает этот MAC после истечения/очистки записи.
- L3: адрес/маска/шлюз/DNS соответствуют плану, нет асимметричного маршрута.
- ACL: разрешённые потоки проходят; контрольные запрещённые потоки не
  проходят; нет временного широкого allow.
- Сервис: функциональный тест владельца, не только ICMP/TCP connect.
- Интеграции: AD/DNS/NTP/SMTP, monitoring, backup, syslog, обновления,
  reverse proxy, NAT и site-to-site routes.
- Для Exchange: DatabaseCopyStatus, activation preference, queues,
  ServerComponentState и cluster node status.
- Зафиксировать фактический результат, изменения адресов и остаточные риски в
  recovery-note и Wiki; вернуть DNS TTL после стабилизации.

## 8. Общий откат

Откат выполняется в обратном порядке только для текущей волны:

1. остановить изменённые сервисы/ВМ;
2. вернуть gateway IP на прежний bridge и прежние firewall/NAT rules;
3. вернуть исходные VM tag/IP/mask/gateway/DNS;
4. вернуть DNS/address-list/monitoring/backup definitions;
5. включить сервисы и повторить baseline;
6. целевой SVI оставить disabled/no-IP до разбора причины.

Не откатывать ранее стабилизированные волны из-за ошибки последующей волны.
Не удалять подготовленный L2-транспорт до завершения всей миграции.

## 9. Точки обязательного согласования

До исполнения нужны решения владельцев по четырём вопросам:

1. окончательная зона VM112 nginx, VM125 FTP, VM129 KSMG и VM130 HAProxy;
2. новый адрес KSC и полный адресный план VLAN1200/1202/1100;
3. назначение VM126/10.78.4.253 и маршруты пользовательского VPN;
4. допустимые сервисные окна для Directum, RDS/1C, tenant-сегментов,
   AD/DNS и Exchange DAG.

После этих решений план можно превратить в точные per-wave command sheets с
готовыми командами AL-OBIT/PVE/guest OS и однозначным автоматическим откатом.
