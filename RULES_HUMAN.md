# Базовые Правила Работы

Дата: 2026-04-02
Владелец: admin-al
Статус: человекочитаемая сводка правил из `RULES.json`

## Язык И Стиль

- По умолчанию всегда работать на русском языке.
- На другой язык переходить только если пользователь явно попросил.
- Не смешивать русский и английский без необходимости.
- Отвечать кратко, практично и по делу.

## Главные Источники Контекста

- `~/ai` является главным operational control plane.
- Основной workflow-файл: `~/ai/WORKFLOW.md`.
- Реестр активных репозиториев и recovery-файлов: `~/ai/PROJECT_CONTEXTS.md`.
- Машинный инвентарь системы: `~/ai/system_inventory.json`.
- Человекочитаемая сводка по системе: `~/ai/system_inventory_human.md`.
- Хронологический журнал действий: `~/ai/actions.log`.
- Тематические recovery-файлы: `~/ai/recovery/`.
- Архив импортированных файлов с другой машины: `~/ai/archive/imported-home-pc/`.

## Главный Фокус На Этом ПК

- Основной тип задач: системное администрирование и сопровождение пользовательской среды.
- Базовые рабочие репозитории: `~/ai` и `~/dotfiles`.
- Все, что меняет систему, пользовательскую среду или live-конфиги вне обычного проекта, считается `system work`.

## Правила Загрузки Контекста

- Нельзя сканировать домашний каталог целиком без явной причины.
- Сначала нужно смотреть базовые файлы в `~/ai`.
- Topic-specific recovery-файлы нужно открывать только когда они реально нужны текущей задаче.
- Если задача чувствительна к версиям, пакетам, сервисам или путям бинарей, сначала нужно использовать `system_inventory`.
- Всегда выбирать минимально достаточный контекст.

## Правила Для Репозиториев

- Для `~/ai` и `~/dotfiles` приоритетом являются дискретные коммиты законченных изменений.
- Если шаг завершен и репозиторий уже существует, по умолчанию его нужно доводить до commit.
- Push делать по умолчанию для завершенного шага, если пользователь явно не запретил и если работа действительно готова.
- Нельзя смешивать в одном коммите несвязанные правки.
- Если работа идет вне git-managed области, нужно оставить recovery trail в `~/ai`.

## Модель Работы С Системой

- Любая работа вне обычного проектного репозитория считается `system work`.
- `~/ai` является управляющим слоем для `system work`.
- Для сведений о пакетах, версиях, бинарях и user services первичным источником считается `~/ai/system_inventory.json`.
- Если инвентарь свежий, не нужно повторно перепроверять установку и версии пакетов без необходимости.
- Для свежести инвентаря использовать TTL:
  - package_versions: 72 часа
  - user_services: 24 часа
  - tool_paths: 72 часа
- Если нужная секция stale или invalidated, ее можно перепроверять точечно сразу.
- После заметных системных изменений нужно обновлять инвентарь или помечать нужную секцию stale.
- Любое нетривиальное системное действие должно оставлять след в `~/ai/actions.log`.
- Любое нетривиальное системное изменение должно иметь recovery trail в `~/ai/recovery/` или обновление существующей recovery-заметки.

## Что Обязательно Фиксировать Для System Work

- что изменено
- зачем изменено
- как проверено
- как откатить или что откат ручной
- нужен ли relogin, restart или reboot

## Что Считать System Work

- изменения в `~/.config`
- user services в systemd
- shell-конфиги
- установка и удаление пакетов
- сетевые настройки
- autostart
- WM, compositor, terminal, notifications
- скрипты в `~/.local/bin`
- bootstrap и миграция окружения
- изменения вне git-репозиториев, которые влияют на состояние системы

## Политика Отката

- Если изменение git-managed, откат предпочтительно делать через git.
- Если изменение вне git, нужно оставить rollback-команду, чеклист или явную пометку, что откат ручной.
- Нельзя оставлять системное изменение без понятного recovery trail.

## Безопасность

- Нельзя выполнять разрушительные операции без явного подтверждения пользователя.
- Нельзя массово переписывать конфиги без rollback-плана.
- Для SSH, network, login, boot и display-related изменений сначала нужно определить безопасный способ отката.
- Нужно предпочитать зарегистрированные recovery-файлы и инвентарь, а не догадки.
